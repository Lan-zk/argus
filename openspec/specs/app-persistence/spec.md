# app-persistence Specification

## Purpose
定义应用状态的持久化与恢复行为：保存配置与最近一次审阅、重启后恢复、API Key 的安全存储、界面偏好记忆。

## Requirements

### Requirement: 应用状态保存范围

系统 SHALL 持久化保存：模型配置、Review Category（含 Prompt 及其版本历史）、当前输入文本、全部审阅项目及其轮次（含文档、运行、Findings 与报告）。存储 SHALL 采用应用数据目录下的本地 SQLite 数据库，保存对用户透明，MUST NOT 要求用户手动保存。API Key MUST NOT 写入数据库，SHALL 继续通过系统安全存储能力保存，数据库中仅存引用。

#### Scenario: 重启后配置仍在

- **WHEN** 用户配置了模型与自定义类别后重启应用
- **THEN** 所有配置与类别（含 Prompt 修改）原样恢复

#### Scenario: 全部项目与轮次持久化

- **WHEN** 用户拥有多个项目且各含多轮审阅，重启应用
- **THEN** 项目列表与每轮完整快照均可恢复查看

### Requirement: 恢复审阅工作区

应用重启后 SHALL 恢复项目列表并回到用户最后活动的项目与轮次，恢复时 MUST 提供明确的恢复提示。轮次审阅发生中断（应用退出或崩溃）时，已落库的部分结果 SHALL 可查看，且该轮 SHALL 被明确标注为未完成。

#### Scenario: 重启回到最后活动位置

- **WHEN** 用户在项目「A」的 Round 2 工作台关闭并重新打开应用
- **THEN** 应用恢复到项目「A」Round 2 的工作台并显示恢复提示

#### Scenario: 中断轮次的部分结果可见

- **WHEN** 某轮审阅进行中应用崩溃，重启后打开该轮
- **THEN** 已完成类别的结果可查看，未完成部分明确标注，整轮标记为未完成状态

### Requirement: 存储迁移与版本兼容

数据库 SHALL 记录 schema 版本；应用启动时 SHALL 将低版本数据库按序迁移至当前版本，每个迁移步骤 SHALL 原子生效（经单连接事务执行，或经幂等可重放步骤达到等效效果），失败时 MUST NOT 留下半完成状态。检测到旧版 JSON 存储文件且数据库尚未完成首次迁移时，系统 SHALL 自动执行一次性迁移：设置全量迁入，最近一次审阅结果转为「导入的审阅」项目的第一轮。首次迁移完成前旧 JSON 文件 MUST 保留在原路径（副本式备份），迁移以库内完成标记防止重复执行，迁移失败后下次启动 SHALL 可重试。数据库版本高于应用已知版本时，应用 MUST 以只读方式工作并提示用户升级。

#### Scenario: 旧数据自动迁移

- **WHEN** 带有旧版 `argus-store.json` 的用户首次启动新版本
- **THEN** 设置与最近一次审阅自动迁入数据库，审阅结果出现在「导入的审阅」项目中，完成后原文件以备份副本形式保留

#### Scenario: 迁移失败可重试

- **WHEN** 首次迁移过程中发生错误
- **THEN** 原 `argus-store.json` 仍在原路径且完好，应用提示迁移失败原因，下次启动重新尝试迁移

#### Scenario: 降级只读保护

- **WHEN** 应用打开的数据库 schema 版本高于自身已知版本
- **THEN** 应用以只读方式呈现数据并提示需升级应用，不产生任何写入

### Requirement: API Key 安全存储

API Key 属于敏感信息：系统 MUST NOT 以明文形式长期存储在普通数据文件中，SHALL 使用系统安全存储能力保存；日志与错误信息 MUST NOT 包含完整 API Key。

#### Scenario: Key 不落明文文件

- **WHEN** 用户保存一条含 API Key 的模型配置
- **THEN** 应用数据文件中不出现该 Key 的明文，Key 通过系统安全存储能力读取

#### Scenario: 界面不回显完整 Key

- **WHEN** 用户重新打开一条已保存的模型配置编辑界面
- **THEN** API Key 字段以脱敏形式显示，不完整回显

### Requirement: 界面偏好记忆

系统 SHALL 保存并恢复用户的界面偏好，至少包括工作台左右分栏宽度。

#### Scenario: 分栏宽度恢复

- **WHEN** 用户调整分栏宽度后重启应用
- **THEN** 工作台恢复上次使用的分栏宽度

### Requirement: Finding 多锚结构存储与兼容

Finding 的主锚、行范围与引用锚结构 SHALL 随审阅结果完整持久化并可在重启恢复后还原全部锚点信息。存储迁移 MUST 幂等可重放且不破坏既有 Finding 数据；迁移 MUST 附带覆盖新旧结构的历史版本脱敏样本校验。兼容行为 SHALL 满足双向可读：

- 读取不含多锚结构的历史数据时，系统 SHALL 将其既有单锚字段还原为主锚形态，显示行为不回退；
- 旧版本应用读取迁移后的存储时，SHALL 仍能以既有单锚字段显示该 Finding 的主锚（多锚信息丢失但不产生错误数据）。

#### Scenario: 新结构重启恢复

- **WHEN** 用户完成一次含行范围主锚与引用锚的审阅后重启应用
- **THEN** 恢复后的 Findings 保留全部锚点信息（主锚范围与引用锚位置），高亮与定位行为与重启前一致

#### Scenario: 历史数据读入为主锚形态

- **WHEN** 应用读取本变更之前产生的审阅数据
- **THEN** 每条 Finding 以既有单锚字段合成为主锚形态，显示行为与本变更前一致，无数据丢失

#### Scenario: 迁移幂等可重放

- **WHEN** 存储迁移在同一数据库上重复执行（如升级中断后重跑）
- **THEN** 迁移步骤安全重放，不产生重复列或数据损坏

#### Scenario: 旧版本应用读新库

- **WHEN** 迁移后的数据库被不支持多锚结构的旧版本应用打开
- **THEN** 旧版本仍从既有单锚字段读到每条 Finding 的主锚并正常显示，不出现错误定位或崩溃
